# D004 工作区标记

- 状态：已定（文件为准 + 按需扫描）
- 日期：2026-10-21

## 背景

DSH 的 Workspace 记录只有 `{id, path, title, sessionIds}`，没有 kind/metadata。需要可靠识别「这个工作区是酒馆」，并且要跨重启、跨工作区删除重加、跨机器迁移都成立。

### 为什么不能直接给 workspace 记录加字段

| 层面 | 原因 |
|---|---|
| 数据契约 | workspace 记录是 storage domain 里的 zod 校验记录（`defineDomain`，当前 version 2）。域由所属包声明且单例打开：第三方不能声明同名域（`already-open`），也不能往别人的域里加表。 |
| 字段保留 | `workspaceRecord` 是 `z.object({...})`，默认 strip 未知字段。手工塞进去的字段在下一次读取/写入校验时被剥掉。 |
| 版本迁移 | 域打开时校验版本和每条记录；改 schema 必须升 domain 版本并手工迁移旧数据，版本不符直接拒绝打开（`version-mismatch`，无自动迁移）。 |
| 类型契约 | `Workspace` 是封闭的 consumer interface，没有 metadata 槽位、没有 declaration merging 钩子；RPC 的 `WorkspaceView` 同样封闭。 |
| 行为约束 | Registry 每次 mutation 用校验后的记录整体重写，且有 two-write/pending-marker 的完整性机制，不会保留未声明字段。 |

只有改 DSH 核心（改所属包的 spec + 升版本 + 迁移 + 持久化格式承诺）才能做到，代价是上游升级维护。第三方插件的正确扩展方式是另起一个自己的 domain（用 `WorkspaceId` 做外键）或在目录里放文件——这正是本决策选择文件标记的原因。


## 候选方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 命名约定 | 标题加 🍺 前缀/后缀 | 零成本 | 用户改名即失效；只能当提示，不能当依据 |
| DSH storage sidecar | 插件 domain 按 `WorkspaceId` 存标记 | 不写用户目录；查询快 | DSH_HOME 重置或换机即丢失；工作区删除重加会换 id；不能随目录备份 |
| **目录标记文件** | 目录内写 `.dshtavern/tavern.json` | 随目录携带、可备份、重注册即恢复；语义直观 | 需要写用户目录；需要文件系统探测 |
| 会话 preset 推导 | 有 tavern 会话就认为工作区是酒馆 | 零额外存储 | 空酒馆无法识别；不可靠 |

## 倾向方案

**目录标记文件为唯一事实来源，内存扫描做快路径。** DSH storage 只在需要时做 UI 状态缓存（v1 可以不做）。

理由：酒馆的工作区目录本来就是它的数据根（角色卡、世界书、提示词模板都放这里），标记跟着数据走最自然；DSH 的 workspace 删除只是注销注册，不删目录，所以「删除后重新添加」时标记文件还在，能自动恢复。

## 标记结构

```text
<酒馆目录>/
├─ .dshtavern/
│  ├─ tavern.json        # 唯一必需文件：标记 + 版本 + 身份
│  └─ state/             # 可重建的插件缓存（可删）
├─ characters/           # 角色卡（可见，便于备份/导入）
├─ lorebooks/            # 世界书
└─ prompts/              # 提示词模板与预设
```

```json
{
  "schema": 1,
  "kind": "dshtavern",
  "tavernId": "<uuid>",
  "createdAt": "2026-10-21T00:00:00Z",
  "title": "雾都夜话"
}
```

## 检测规则

| 要判断什么 | 规则 |
|---|---|
| 会话是否酒馆模式 | `session.header.cwd` 目录下存在 `.dshtavern/tavern.json` |
| 工作区是否酒馆工作区 | `workspace.path` 目录下存在同一标记 |

- 两者用同一份标记，互不依赖：会话靠 cwd 直接判断，不需要先查工作区 id。
- 嵌套目录不识别：只有「目录本身带标记」才算，父目录是普通工作区不影响子目录。
- 不靠命名/标题做判定，标题只用于显示。

## 生命周期

| 场景 | 行为 |
|---|---|
| 新建酒馆 | 建目录 → 原子写 `tavern.json` → 注册工作区。注册失败可重试，标记已落盘不会丢 |
| 收编已有工作区 | 在目标目录写标记（UI 明确列出将写入的路径），然后刷新为酒馆 |
| 取消标记 | 删除 `tavern.json`，保留数据；已有会话保持原 preset，新会话回到普通模式 |
| 删除工作区 | DSH 只注销注册，不删目录；重新添加同一目录时标记仍在，自动恢复为酒馆 |
| 目录移动/重命名 | workspace 路径失效；注册新路径后靠标记重新识别，不依赖 `WorkspaceId` |
| 换机器/DSH_HOME 重置 | 标记在目录里，重新注册即恢复 |
| 目录不可读/缺失 | 当作「标记未知」；UI 显示目录缺失，不自动取消酒馆身份 |
| 标记损坏或被改 | 结构校验失败时按未标记处理，并在 UI 提供修复入口 |

## 对账时机（DSH 没有工作区事件）

启动扫描已注册工作区 → 自己的创建/收编动作 → `session/created`（按 cwd 读标记）→ 客户端主动刷新（workspace follow 的 upsert/remove 时触发）。

## 写安全

- 用宿主侧文件系统原子写（临时文件 + rename），UTF-8 JSON。
- 只写自己拥有的 `.dshtavern/`，不碰用户其他文件。
- 标记带 `schema` 版本；遇到更高版本时只读并提示，不静默改写。
- 写入只发生在用户显式的「新建酒馆 / 收编为酒馆」动作里，不做后台自动写。

## 与 preset 的关系

- 标记只决定「新会话该用哪个 preset」；一旦会话进入 tavern preset，会话侧插件不需要再判断标记。
- 客户端创建会话时显式传 `agentPreset: 'tavern'`；宿主在 agent 创建前/创建时按 cwd 标记兜底纠正。

## 已确认的默认设定

1. 标记目录使用 `.dshtavern/`（标记与数据统一放在其下）。
2. v1 不做持久化 sidecar；目录缺失时按「标记未知」处理，界面显示目录缺失。
3. 取消标记只影响新会话：已有会话保持原 preset，并在界面提示。

## 原待定项（已由上面的默认设定回答）

- 标记目录用隐藏风格的 `.dshtavern`，还是可见的 `tavern/`。
- v1 是否需要持久化 sidecar。
- 取消标记时，已有会话是否强制切回 standard preset。
